# Security policy

This application holds **read-only credentials to somebody's production
database**, and its whole job is to read execution history out of it. That
raises the stakes above what a dashboard usually carries, so security reports
are genuinely welcome.

## Reporting a vulnerability

**Please do not open a public issue for a security problem.**

Use [GitHub's private vulnerability reporting](https://github.com/giorgoskoufos/n8n-analytics/security/advisories/new)
— the **Report a vulnerability** button under the repository's Security tab. It
creates a private advisory that only maintainers can see, and it gives us a
place to work on a fix and a disclosure together.

Include, if you can: the version (`GET /api/version`, or Settings → Health), how
you deployed, and enough detail to reproduce.

### What to expect

Honest expectations for a solo-maintained project:

| | |
|---|---|
| First response | Within about a week |
| Assessment | Within two weeks of the first response |
| Fix for something confirmed and serious | As a patch release, as soon as I can |

If you have not heard back in two weeks, please ping the advisory — it means it
was missed, not ignored.

I will credit you in the advisory and the changelog unless you would rather I
did not. There is no bounty; this is a free community project.

## Supported versions

| Version | Supported |
|---|---|
| 2.x | Yes |
| 1.x | No — please upgrade |

Fixes ship on the latest minor. There is no backporting to older minors.

## In scope, and worth looking at

These are the areas where a finding would matter most, roughly in order:

- **Authentication and session handling** — `src/middlewares/auth.js`, the login
  path, token issuing and expiry, and the role checks that gate elevated
  actions.
- **The AI assistant's sandbox.** The assistant can write read-only SQL against
  a restricted set of views. The defence is layered — a connection opened
  `OPEN_READONLY` so no statement can write whatever it says, `ai_*` views in
  which payload columns are absent rather than merely filtered, row scoping
  applied inside those, and a regex guard last and weakest. **A way to read a
  column that is not in those views, or to reach data outside the caller's
  scope, is a real finding.** `AI_SQL_TOOL=off` disables the capability
  entirely.
- **Alert delivery and SSRF.** Alert targets are user-supplied URLs. They are
  validated against private and loopback addresses, and link-local ranges
  (169.254.0.0/16, fe80::/10 — the cloud metadata endpoints) stay blocked even
  when `ALERT_ALLOW_PRIVATE_TARGETS=true`. A bypass of that is a real finding.
- **Anything that writes to the n8n PostgreSQL.** The ETL is read-only by
  design. A path that issues a write against the source database is a serious
  bug regardless of whether it is reachable by an attacker.
- **Secret handling** — the JWT secret, the OpenAI key stored in the dashboard's
  own database, and alert channel headers, which are masked in the UI and in the
  generated `curl` examples.
- **The frontend.** A strict CSP with `script-src 'self'` and
  `script-src-attr 'none'` is a load-bearing control here, not a checkbox. A way
  to get script execution past it, or a stored-XSS route through workflow names
  or error text pulled out of n8n, is in scope.

[documentation/security](documentation/security) describes each of these in more
depth, including what is deliberately *not* copied out of n8n.

## Out of scope

- Anything requiring an already-authenticated administrator. An admin can
  configure the app; that is the feature.
- Missing hardening headers with no demonstrated impact.
- Denial of service through sheer request volume. Rate limits exist, but this is
  an internal tool and is expected to run behind your own network boundary.
- Vulnerabilities in n8n itself — report those to
  [n8n](https://github.com/n8n-io/n8n/security).
- Reports generated by a scanner with no analysis attached.

## Deploying this safely

Not vulnerabilities, but the three things that most affect how exposed an
install is:

1. **Give it a read-only PostgreSQL role.** The application never writes to your
   n8n database. A read-only role turns that from a promise into a guarantee.
2. **Do not expose it to the internet** unless you have put authentication in
   front of it that you trust. It is designed to sit inside your own network.
3. **Set `DASHBOARD_JWT_SECRET` to something you generated**
   (`openssl rand -base64 48`). The server refuses to start on anything shorter
   than 32 characters, but short-and-valid is still guessable.
